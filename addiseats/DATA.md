# Data Fetching

The food catalog is a small local dataset in `lib/data.js`; order data is held in the demo's in-memory server store. Private order queries always use the current session identity. Client query keys below are the SWR keys (or `null` when no request should run).

| Data / query | Execution | Query key or source | Refresh / revalidation | Why |
| --- | --- | --- | --- | --- |
| Public menu initial data | Server (`app/menu/page.js`) | `getMenuPage({ search, category, sort, page })` over `lib/data.js` | Local catalog data; no remote revalidation interval is needed. The route remains publicly renderable/indexable. | Search engines receive the menu HTML and metadata from the server; static catalog data has no changing backend to poll. |
| Dish detail and metadata | Server (`app/menu/[id]/page.js`) | `getDish(id)` | Same local catalog source as the menu; rebuilt when the catalog changes. | The initial content, structured data, metadata, and social preview all use the same dish record. |
| Typed menu search | Client (`app/menu/SearchBox.jsx`) | `['/api/dishes', debouncedSearch, category, sort, page]`, or `null` while search is empty | Search is debounced by 300 ms; SWR explicitly revalidates on mount/key activation, keeps previous data while loading, deduplicates identical requests for 2 seconds, and does not revalidate on focus. No `staleTime` is configured (SWR's default revalidation behavior applies). | This query is caused by typing. The debounce avoids per-keystroke requests; an empty search uses the already-server-rendered local results instead. |
| Order history | Server (`app/orders/page.js`) | `getOrdersForUser(session.id)` | Request-time read of the current in-memory store; no client polling. | Private data is rendered server-side and is always scoped to the signed-in user. |
| Order detail/status initial data | Server (`app/orders/[id]/page.js`) | `getOrderForUser(id, session.id)` | Request-time owner-scoped read. Its result seeds the client status query. | The first status is available in server HTML without an initial loading spinner, and the requested ID cannot select another user's order. |
| Live order status | Client (`app/orders/[id]/OrderStatus.jsx`) | `/api/orders/${id}` | SWR `fallbackData: { order: initialOrder }`; poll every 5 seconds, including hidden tabs; no focus revalidation; deduplicate for 1 second. | The server result is shown immediately; five seconds is a modest freshness interval for kitchen progress, and background polling keeps a customer order tab current while staff use the kitchen. |
| Order confirmation | Server (`app/order-confirmation/[id]/page.js`) | `getOrderForUser(id, session.id)` | Request-time, owner-scoped read. | Private order details are rendered only after server authentication and ownership checks; no client-side bootstrap request is needed. |
| Pagination | Server initial render (`app/menu/page.js`) and client (`app/menu/SearchBox.jsx`) | URL query `?page=N`; search SWR key includes the page as its final element | Page changes update the query string and displayed local or searched results. Search requests retain the page in their stable key; changing search/category/sort resets to page 1. | The URL is shareable and refresh-safe; both local browse pages and typed-search results use the same six-item page size. |
| Cart | Client (`components/CartClient.js`, checkout client) | Browser `localStorage` key `addisEatsCart`; no SWR key | Updated immediately on cart actions and shared through the `addis-cart-updated` browser event. | A cart belongs to the current browser and must be usable before signing in. The server recalculates prices from catalog IDs at order submission. |
| Favorites | Client (`app/favorites/FavoritesClient.jsx`) | Browser `localStorage` key `addisEatsFavorites`; no SWR key | Updated on user action and restored from local storage on mount. | Favorites are a browser preference and do not require a server query. |

`GET /api/dishes` implements the typed-search response and validates category/sort input. `GET /api/orders` and `GET /api/orders/[id]` are authenticated API equivalents of the server order queries; the latter returns 404 for both an unknown ID and an order owned by another user. `POST /api/orders` independently authenticates, validates the request, and sets the owner from the session rather than the body. The kitchen status mutation is a server action (`updateOrderStatus` in `app/actions.js`), not a client-side store update: it verifies the staff role, saves to the existing order store, and revalidates order and kitchen paths. Customer status polling continues through the owner-scoped `/api/orders/[id]` query.
